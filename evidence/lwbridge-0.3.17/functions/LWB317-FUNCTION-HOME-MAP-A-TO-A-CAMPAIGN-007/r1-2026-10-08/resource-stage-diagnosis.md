## Actual production pipeline and observation mechanics

1. `CurrentClientMap317ScanProvider.ActivateAcceptedRun` constructs the actual `MapScanEngine`, `Map317ScanRunSink`, `MapControlPlane` and a session-owned provider cancellation token. Source `CurrentClientMapBlockSource.FastCity.cs` enters `CaptureFullCityMapAsync` on `pendingBlockIndices.Count == 2500 && seedBlock.BlockIndex == 0`. It collects a whole-world AOI/resource footprint into in-memory state then returns a **2,500-capture** batch to `MapScanEngine`. Acquisition percent callbacks can occur before any block returns.
2. `MapScanEngine.ExecuteAsync` **awaits that entire batch before any** `Map317ScanRunSink.CheckpointSuccess`. A 47%-acquisition-progress callback can truthfully coexist with `completed=0`, durable `staged=0` and old published data. `Map317ScanRunSink` stages records only after batch validation. The engine then processes block completions and enters the `publishing` transition, calling `control.CompleteScan()` to atomically replace selected-kind publication.
3. Production `MapScanStateMachine.StopAsync` first commits durable `store.CancelScan(runId)` (delete staged data), then asks the provider to cancel/await the active engine even if caller token is canceled, then moves the in-memory state to idle. A provider returning after cancellation is an actual race at this seam.
4. The pre-R1 engine did **not** check the cancellation token **after** the awaited capture returned; the original `MapStore.StageRecord` accepted inserts to `scan_records` for a durable `cancelled` run. A gated provider deliberately returning two blocks after cancellation reproduced `status=cancelled, staged=2, published=1, isReading=false` (retained `late-stage-baseline-failure.json`). This is a genuine current-production defect against the recovered original high-level canceled-staging rule; no original protected provider execution was needed to distinguish it.
5. Narrow repairs: `MapScanEngine.cs` rejects a canceled token immediately after the capture await and before batch checkpoint; `MapStore.StageRecord` under the existing SQLite lock independently verifies `scan_runs.status='running'` for the exact run/server, rejecting canceled/failed/missing runs with `INVALID_SCAN` even before the in-memory state reaches idle. This also covers cancellation between token check and sink write. **No traversal, wait, retry timing, acquisition, stage publication schedule or gameplay behavior was modified**.
