## Remaining concrete ownership cases

### H2-HOME-01 — Starting-owner cancellation still overwrites a foreign marker [P1, source trace]

`OverviewLifecycleService.Close` captures a starting owner's session/challenge and calls `TryWriteStartCancellationMarker` (`OverviewLifecycleService.cs:412-430`). The request-cancellation registration also invokes it (`:1076-1084`). `WriteStartCancellationMarker` creates its own temporary file, then uses `File.Move(temp, path, overwrite: true)` for shared `cancel-start.txt` (`:1519-1537`). It never checks whether the existing destination belongs to that session/challenge. Thus, if shared cancellation storage currently contains foreign owner B's marker, cancellation/Close of still-starting A replaces B's bytes with A's marker. This directly conflicts with RECOVERY-002's requirement to preserve foreign cancellation files, even though later cleanup checks metadata.

`WriteLease` similarly overwrites `lease.txt` without validating an existing foreign session (`:1490-1502`). Normal composition still uses the existing shared application runtime directory (`:113`), so injected-root safety does not prove production contention safety. This review does not claim a foreign owner's file was actually changed; the exact overwrite path is the finding. The expected source-supported single owner must be enforced at the shared-file admission/write boundary, or writes must fail closed when another owner holds those files. Preserve current-client protocol paths.

Distinguishing offline proof: use one temporary shared directory, an inert deferred-start A and foreign B cancellation/lease bytes; cancel/Close A and retain B's bytes. Also distinguish timer A attempting a lease refresh after the file belongs to B. Do not place a sentinel in real LocalAppData. Current `VerifyInactiveLifecycleCleanupIsolation` (`ProfileRuntimeOwnerChecks.cs:174-255`) exercises only inactive lifecycles, so no non-null starting session writes a marker and no lease timer writes in those cases.

### H2-HOME-02 — Lease cleanup checks bytes and deletes a path in separate operations [P2, source interleaving]

`TryDeleteOwnedRuntimeFile` performs `File.ReadAllBytes(path)`, validates session/challenge, then calls `DeleteFile(path)` (`OverviewLifecycleService.cs:1628-1641`; actual deletion `:1755-1758`). No open file handle or cross-owner transaction protects the verified file identity until deletion. The surrounding `leaseWriteGate` is instance-local (`OverviewLifecycleService.cs`, field declaration), so it cannot serialize another native owner/process atomically replacing the shared path. Interleaving: A reads an A-owned lease; B replaces the path with a B-owned lease; A deletes the path using the old ownership decision. Metadata validation is useful but does not establish deletion of the same file that was validated.

Required distinction: protect the actual file identity during conditional deletion or enforce a shared ownership transaction covering both validation and mutation. Offline test should substitute foreign bytes/file identity between validation and deletion and require preservation. The current inactive sentinel check establishes the null-session short circuit, not this matching-session contention branch. This is a source-located concurrency hole, not a demonstrated current owner-session disruption.
