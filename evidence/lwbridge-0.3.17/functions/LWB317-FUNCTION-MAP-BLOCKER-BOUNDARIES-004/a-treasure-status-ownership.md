## Exact frontend ownership

The retained status wrapper is a no-feature-payload call, but it is not truly unscoped. The generic bridge wrapper injects the **currently selected** `profileId` into every call that does not already carry one. The selected-profile injection is at frontend index offset `200777`; the status wrapper is at `207739`.

Therefore the absence of a Treasure UUID/records payload proves only that the caller does not pass those records on each status poll. It does **not** prove the provider cannot return per-target state from provider-owned/controller state created earlier.

The claim poll also does not pin the initiating profile ID. Every poll re-enters the generic wrapper, which reads the selected profile at that invocation. The exact poll has no separate profile equality test or cancellation token. This is an observable frontend ownership edge; this audit does not invent how the original native/provider resolves a profile switch during a still-running React callback.

## Idle snapshot versus active batch

The Treasure context effect calls status before any claim. At Map-panel offset `32253` it consumes:

- `playerUid`;
- `allianceId`;
- `states`.

It merges `states` by each state's `uuid`; `states` may be an array or object-valued collection. An active `batch` is not required for this idle snapshot.

After `map_treasure_claim` returns, the frontend starts status polling only if `queued > 0` (offset `40198`). It then:

- waits 1,000 ms before each status read (`40255`);
- runs at most 1,800 iterations (`40209`), approximately 30 minutes;
- merges every returned `states` snapshot (`40300`);
- continues when `batch` is absent;
- continues while `batch.state == "running"`;
- stops when `batch` exists and `batch.state != "running"` (`40373`), then forces data refresh;
- exits through the claim error path on a thrown status error and always clears the frontend busy flag.

This is strong source evidence that an active `batch` may be provider-owned state established by the earlier claim operation. It is also strong evidence that the status provider must have an idle snapshot path independent of an active batch.

## Distinguishing hypotheses

| Hypothesis | Disposition | Source reason |
|---|---|---|
| No UUID input means per-target status cannot exist | **REJECTED** | Status is profile-scoped and consumes cached `states`; polling follows a prior claim that can establish provider-owned controller state. |
| Status is only the active claim batch | **REJECTED** | Treasure-tab entry calls status before any claim and consumes identity/states while `batch` may be absent. |
| Status can read an active batch/cache created by prior claim | **PARTIALLY SUPPORTED** | Polling starts only after `queued > 0`, no claim rows are resent, and optional `batch` drives completion. Private storage/lifecycle is not recovered. |
| Idle `states` must be freshly queried per target on each status call | **UNKNOWN / NOT REQUIRED BY OBSERVABLE CONTRACT** | Frontend does not supply records. Provider could read current game state, a cache, or a controller-owned snapshot. |

## First genuine missing edge

`provider-owned idle state snapshot + active claim controller/cache -> exact status snapshot {playerUid, allianceId, states, optional batch}`.

Static artifacts do not currently expose:

- where the high-level provider stores its idle `states` or active batch;
- exact batch initialization fields/default values beyond the frontend-observed `state`;
- the complete terminal batch-state vocabulary or counter transitions;
- reset/retirement rules after terminal completion, provider error, timeout, reconnect, profile change or a later claim;
- whether idle states are recomputed or cached;
- exact provider behavior when the profile changes during a still-running frontend poll.

Minimum evidence to settle those points is the protected high-level status/claim controller body, another artifact that defines that cache/controller, or a future explicitly authorized live witness covering idle -> running -> terminal/reset for one profile and a profile-change case.

## Ready offline work

Without enabling Treasure claim execution, a future implementation task can independently model/test the **host/frontend-owned** status envelope and profile-scoped polling ownership: idle identity/states, optional batch, merge-by-UUID, running/terminal polling, and retirement on selected-profile generation changes. That work must not invent the missing provider batch transition schema.
